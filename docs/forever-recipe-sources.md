# Forever beta recipe sources and API evidence

Checked 2026-09-27. This is a source assessment, not a claim that recipe capture is ready to ship. It distinguishes the installed beta client and user-supplied probe from documentation for other WoW products.

## Finding

Prefer the **Forever client's own `C_TradeSkillUI`** for learned recipes, outputs, and reagents. The user's build `1.60.1.70009` / interface `16001` probe, run with a profession window open, returned `GetFilteredRecipeIDs` (22 IDs) and `GetAllRecipeIDs` (at least 200; the probe caps its count at 200). It sampled three IDs: all three `GetRecipeInfo` calls returned tables with `learned=true`; all three schematic calls returned tables, numeric outputs and quantity ranges, and four exact item/quantity reagent slots with no ambiguous slots. These are observations from the user's screenshot, [the project's probe code](../GamersTrackerForever/BetaProbe.lua), and [probe procedure](forever-beta-probe.md), **not** a complete profession or learned/unlearned test. The sample favors the filtered list, so three `true` flags cannot prove that `GetAllRecipeIDs` is complete or that `learned=false` works.

Yes, **numeric recipe IDs plus `GetRecipeInfo(id).learned` are the plausible way to distinguish learned from unlearned**. The retail client-generated [TradeSkill UI API types](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TradeSkillUITypesDocumentation.lua) include both `recipeID` and boolean `learned` in `TradeSkillRecipeInfo`; its [API signature](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TradeSkillUIDocumentation.lua) calls the argument to `GetRecipeInfo` a `recipeSpellID`. The beta probe confirms the beta returns a `learned` boolean for the three sampled IDs. For capture, enumerate the **all** list rather than the UI-filtered list, call `GetRecipeInfo(id)`, and retain only verified `learned == true` entries. Validate at least one known unlearned recipe and multiple professions first. Filtering matters: the 22 visible IDs cannot safely be treated as the complete learned set, and an empty/partial scan must not erase previously saved recipes.

An ID-level comparison should check `(requested ID, info.recipeID, info.name, info.learned, schematic.recipeID)` for a known learned and a known unlearned entry. Require matching numeric IDs and a real boolean; do not infer `false` from an absent info table. Compare that same numeric ID with Wowhead Forever's `/spell=ID` page and manually confirm the name and reagent identities. This validates an optional cross-reference; Wowhead cannot supply the per-character `learned` value.

The same retail-generated [types](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TradeSkillUITypesDocumentation.lua) describe `CraftingRecipeSchematic.outputItemID`, `quantityMin/Max`, `reagentSlotSchematics`, each slot's `quantityRequired` and `reagents`, and each reagent's optional `itemID` or `currencyID`. `GetRecipeSchematic` takes a `recipeSpellID` and `isRecraft` according to the [generated signature](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TradeSkillUIDocumentation.lua). These structures fit the desired material display, but the beta must still be checked for multi-option, optional, currency, and missing-output recipes; do not assume every slot is one exact bag item. The retail generated file is **not** the Forever beta API specification: it does not list `GetAllRecipeIDs` or `GetFilteredRecipeIDs` even though the user's beta probe called both successfully. A beta-build-specific generated API dump or repeated in-client probes are stronger evidence for `16001`.

Profession association is a separate gate. The retail-generated API has `GetProfessionInfoByRecipeID`, but the current probe did not test whether that function exists or returns usable information in Forever. It also did not establish whether `GetAllRecipeIDs` is scoped to the open profession, globally indexed, or affected by filters. Record the currently open profession identity and test this mapping before saving a recipe under Blacksmithing, Cooking, etc. [Retail API signature](https://github.com/Gethe/wow-ui-source/blob/live/Interface/AddOns/Blizzard_APIDocumentationGenerated/TradeSkillUIDocumentation.lua); [beta probe implementation](../GamersTrackerForever/BetaProbe.lua).

The [Gethe UI-source branch list](https://github.com/Gethe/wow-ui-source/branches) checked today shows retail (`live`), PTR, and Classic branches, but no identified Forever branch. That is an absence in this mirror, not proof Blizzard publishes no Forever specification elsewhere. We found no first-party, build-pinned **Forever profession API specification** in the sources checked; the installed beta and in-game probe remain the compatibility authority. Do not equate the Blizzard public web API, WoW's in-game Lua API, and Wowhead pages—they have different identifiers, data scopes, and rights.

## Recommended validation before enabling capture

1. With each profession open and no search/filter active, compare visible recipes against `GetAllRecipeIDs`, then deliberately change filters to see whether the all-list remains stable. Check whether its IDs map to the currently open profession; test `GetProfessionInfoByRecipeID` only if the beta exposes it.
2. For a known learned and known unlearned recipe in the same profession, compare `GetRecipeInfo(id).learned` (without storing personal names in diagnostics). If every sampled ID remains `true`, the current probe has not established discrimination.
3. Sample schematics across crafting professions, smelting/gathering, enchanting, and recipes with optional/alternative/currency reagents. Persist exact `itemID + quantityRequired` only when one required item option is unambiguous; otherwise mark materials as unknown/alternative rather than falsely claiming a character can craft.
4. Match several beta `recipeID` values manually to Wowhead Forever **spell** URLs. Use those URLs as optional references, not as the inventory or learned-state database. If a server-side catalog is later desired, obtain licensed source data and design refresh/versioning for changing beta recipes.
5. Add regression fixtures for list completeness, profession mapping, `learned=false`, stale cache preservation, and ambiguous reagents before lifting the Forever recipe gate.

The addon now includes `/gtf recipecheck` as a bounded, read-only implementation
of the ID comparison above. It prints a few learned/unlearned IDs and any
available profession ID without changing filters or SavedVariables. Its live
beta result is still pending; adding the diagnostic does not enable capture.
